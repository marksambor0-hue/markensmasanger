# MARKENS — общий контракт разработки и выпуска обновлений

Этот документ — общая память команды для ChatGPT и Gemini. Рабочий код и правила хранятся вместе в GitHub, а не только в отдельных чатах. Всегда начинай с актуальной ветки `main`.

## Дизайн и поведение

- Не переделывать мессенджер с нуля и не менять без прямой просьбы его тёмный Discord-подобный стиль, ширины панелей, навигацию, расположение чатов и привычные элементы.
- Сохранять все рабочие возможности и текущую схему Firebase. Изменение UI — только если пользователь этого просит или это минимально необходимо для исправления подтверждённого бага.
- При визуальном баге сначала установить причину по коду, скриншоту и diff. Не маскировать симптом случайными CSS-правками.
- Никогда не заменять весь большой `index.html` старой копией из ZIP/архива. Не удалять и не переименовывать файлы без прямого запроса. При сомнении оставлять файл как есть.

## Работа вдвоём

1. Одна общая точка истины — актуальный GitHub `main`, файлы `GEMINI.md` и этот документ. Загрузка из старого архива не считается актуальной версией.
2. Перед правкой прочитать последние коммиты, целевые файлы и состояние Actions. Изменять только нужные строки.
3. Не затирать изменения другого помощника. Перед записью проверять, что `main` не сдвинулся после чтения; если сдвинулся — повторить анализ на новом HEAD.
4. Не допускать удаления существующих файлов. Gemini workflow должен останавливать такой патч, а не публиковать его.
5. Коммиты небольшие и тематические. После каждого изменения сообщать пользователю SHA коммита, перечень затронутых файлов, проверку и честный статус CI.

## Как выпускаем обновления

- Ветка `main` — источник релизной сборки. Push запускает Windows GitHub Actions; релиз публикуется только после тестов и появления установщика и метаданных автообновления.
- Версия в `package.json`, константа `CURRENT_SCRIPT_VERSION` в `index.html`, GitHub Release tag и версия установщика должны совпадать (допускается эквивалентная форма `31.0` и `31.0.0`, если они нормализуются к одному SemVer).
- Для следующего релиза сравнить SemVer из `package.json` с последним опубликованным GitHub Release; использовать больший номер и увеличить patch на 1. Никогда не скатываться на старую линию версий только потому, что последний релиз отстаёт от исходников.
- Вместе с версией обновлять `CURRENT_SCRIPT_TS`; проверять это тестом.
- Сохранять существующий канал доставки: GitHub Releases для Windows автообновления с `MARKENS_Setup.exe`, `latest.yml` и `.blockmap`; не менять канал или Firebase на другой сервис без просьбы пользователя.
- Release notes: кратко и естественно по-русски. Сначала исправления и реальные изменения; затем совместимость или известные ограничения. Не обещать то, что не тестировалось.

## Проверки перед словом «готово»

1. `npm test` зелёный.
2. Windows workflow завершён успешно; наличие `MARKENS_Setup.exe`, `latest.yml` и blockmap подтверждено.
3. Посмотреть итоговый diff и убедиться, что не затронуты несвязанные функции, UI, Firebase и чужие правки.
4. Успешная сборка не равно полному runtime-тестированию. Отдельно сообщать, что реально запускалось, а что всё ещё требует проверки в работающем приложении.

## Ограничения

Не публиковать секреты. Не ослаблять Electron security. Не удалять тесты и не подавлять ошибки ради зелёного CI. Если тест обнаружил настоящую проблему — исправлять причину; если ошибочен сам тест — исправить тест, не выдавая его за баг приложения.
