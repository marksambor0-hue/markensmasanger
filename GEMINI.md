# MARKENS — общие правила разработки для ChatGPT и Gemini

Это единый контракт команды. Перед любым изменением читай этот файл и `DEVELOPMENT_CONTRACT.md`. Если история чата, архив или старый ZIP противоречат актуальному репозиторию, источником истины являются текущая ветка `main` и файлы в ней.

- Это существующий MARKENS — Electron-мессенджер Windows с большой HTML/CSS/JS-реализацией, Firebase и текущим интерфейсом. Не начинай проект заново.
- Стиль пользователя: сохранять узнаваемый тёмный интерфейс в духе Discord/MARKENS, панели, расположение и визуальные привычки. Никакого кардинального редизайна, «улучшений ради улучшений» или удаления функций без прямой просьбы.
- Делай минимальные точечные изменения: сначала выясни причину бага, изучив текущий код и недавние коммиты, затем меняй только нужные строки. Не заменяй целиком `index.html`, `main.js`, `preload.js` или workflow ради маленького исправления.
- Никогда не удаляй/переименовывай существующие файлы, не откатывай чужие изменения и не затирай изменения другого помощника. Не загружай старый ZIP поверх актуальных исходников. Если файл кажется лишним — оставь его и объясни причину.
- Сохраняй Firebase-проект и формат данных, вход/регистрацию, чаты, друзей, личные сообщения, голос/видео, VORTEX, панельки, настройки и Windows 10/11 x64. Не меняй Firebase-конфигурацию или разрешения без необходимости.
- Не добавляй секреты, токены, приватные ключи или пароли в репозиторий. В Electron сохраняй `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; не выдавай микрофон, камеру или демонстрацию экрана автоматически без действия пользователя.
- Перед правкой обнови контекст с актуального `main`, посмотри последние коммиты и состояние CI. После изменения проверь diff: только ожидаемые файлы, никаких удалений и случайной переформатировки огромного HTML.
- После изменений запускай `npm test` и доступные проверки. Для релиза Windows проверь зелёный GitHub Actions, `MARKENS_Setup.exe`, `latest.yml` и blockmap. Не говори «проверено/готово», если проверка ещё выполняется или упала.
- Версия приложения в `package.json`, `CURRENT_SCRIPT_VERSION` в `index.html` и GitHub Release должны соответствовать одному SemVer. Новый релиз выбирает следующую patch-версию от большей из версии в package.json и последнего опубликованного релиза; не публикуй меньшую версию. Build timestamp обновляется вместе с версией.
- Стиль коммитов — короткий и понятный: `fix:`, `feat:`, `docs:`, `test:`. Release notes пиши простым русским языком: что исправлено/добавлено и что важно пользователю, без пустых маркетинговых обещаний.
- Если другой помощник уже меняет ветку или появилась новая версия `main`, сначала перечитай состояние и аккуратно перенеси только свой маленький патч. Не force-push и не переписывай историю.
